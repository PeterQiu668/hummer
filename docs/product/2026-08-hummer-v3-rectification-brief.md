# HUMMER V3 整改意见：从「18 个企业管理页面」回到「一块工作台 + 一台能真动手的机器」

> 日期：2026-08-25
> 对象：下一版可交互原型（V3）
> 关联：`2026-08-market-entry-analysis.md`、`2026-08-technical-product-spec.md`、`2026-08-hummer-v2-prototype-brief.md`、`Hummer-V11-企业级Agent原型优化建议.md`
> 性质：**减法优先的整改**。V3 的第一个 PR 应该是删和降级，不是再加一个页面。

## 0. 先纠正我自己在 V11 里的两条建议

为避免 Codex 在两份文档之间摇摆，这里明确撤销 V11 中的两条判断：

| V11 原建议 | V3 裁决 | 原因 |
|---|---|---|
| 恢复并做成 25—35 秒四幕「上岗仪式」 | **撤销**。压成雇佣弹窗里的一行权限清单 + 一个确认按钮 | 招聘要像 WorkBuddy 一样「雇了就上班」，仪式感在这里是摩擦不是价值 |
| 员工市场恢复为一级、四种浏览方式 + 五步定制 | **降级**。市场收进「团队」页的一个「雇人」抽屉；五步 wizard 移出主路径 | 市场是供给入口，不是日常入口；日常入口只能有工作台 |

V11 其余判断（同一状态链、能力可见、成果包、进化闭环）继续有效，但**全部改为在工作台内以上下文层出现，不再各自占一个一级导航**。

## 1. 诊断：V2「还是太复杂」的真正原因

不是功能多，是**一级对象太多**。

Codex 和 WorkBuddy 前端简洁的机制是：整个产品只有 **一个主对象**（一次任务 / 一个会话），权限、工具、文件、diff、证据、成本全部是挂在这个对象上的**上下文层**，只在需要的那一秒出现。用户永远只在一个面上，从不需要"逛"。

HUMMER 现在是反过来的：

```
src/store/useAppStore.ts:21  PageKey 共 20 个
其中 4 个是 modal 覆盖层（market / lobster / governance / hermes），
和 page 语义混在同一个 setActivePage 里
LeftNav.tsx:47  boss 角色 = 3 组 13 项 + 活跃频道分组（feishu channels）
```

每一个都是一个并列的一级对象，用户要自己去逛完，然后**在脑子里把它们缝成一件事**。这就是"复杂"的来源——不是信息密度高，是**缝合成本转嫁给了用户**。

V2 加「本地执行台」把问题加重了一层：它成了第 20 个入口，而且和 `ExecWorkspacePage`(27.7KB)、`TasksPage`(15KB)、`EvidencePage`(18.4KB) 职责重叠。用户感知到的是"又多了一个入口"，不是"能力变强了"。

三条具体证据：

1. **执行台是个孤岛。** `DesktopWorkstationPage.tsx` 全篇是 `WORKSTREAMS` / `WORKSPACE_ITEMS` / `SESSION_COPY` 三个模块级硬编码常量，不读 store 的任何 domain state。而 `src/features/work-orders/model/workOrder.ts` 和 `resultPackage.ts` 这套真 model 只被 `TrustedWorkOrderPanel` 用。**界面在长，事实源没在长。**
2. **"执行"其实是个四步动画。** `requestSession → approveSession → startSession → pauseSession` 全是 `setState` + `pushAudit` + `pushToast`，没有任何 step、trajectory、工具调用或产物对象。用户看到的"桌面能力"是一段固定的 5 行假日志（`DesktopWorkstationPage.tsx:283-287`）。
3. **招聘路径长得离谱。** `Marketplace.tsx`(33KB, 5 tab: browse/packages/wizard/experts/mine) + `LifecycleBoard` + `TrialReportCard`(20.6KB) + `AuthorizationCeremony`(13.2KB) + `SkillSlotIn`。雇一个人要穿过 4 个组件、上百 KB 的 UI。

结论：

> **V3 不要再优化布局。要把 20 个一级对象砍到 4 个，把省下的全部预算压进「桌面执行」这一件事上。**

## 2. V3 一句话目标

> **HUMMER V3 = 一块 Codex 式的工作台（我在这里看着一群数字员工在我的机器上干活、随时插手），+ 一次 WorkBuddy 式的雇人（30 秒内多一个同事），+ 一套企业才有的责任链（谁批的、动了什么、成果算谁的）。**

前两件决定它好不好用，第三件决定它卖不卖得掉。三件都要，但**只有第一件配得上占据首屏**。

---

## 3. 硬约束（V3 验收线，不满足即打回）

1. 一级导航 **≤ 5 项**；首屏 **只有一个主对象**。
2. 雇一个员工 **≤ 3 次点击、≤ 20 秒**，且不经过 wizard / 试岗报告 / 授权仪式。
3. 主任务全流程（派活 → 执行 → 审批 → 交付 → 打回）**全程不离开工作台页面**。
4. 桌面执行必须有 **可展开的 step 级 trajectory**，每步能看到：工具 + 参数 + 结果 + 耗时 + 花费 + 产物。
5. 任何执行状态下，**停止按钮 1 次点击可达**且常驻可见。
6. 不得新建第 21 个 PageKey。新能力一律以工作台内的层 / 抽屉 / 内联形式存在。

## 5. 改造二：雇佣像 WorkBuddy 一样简单

**新流程（全部 3 步）：**

```
团队页 →「+ 雇一个员工」→ 一屏卡片列表（按岗位）→ 点「雇佣」
→ 一个确认弹窗（3 块信息）→ 确认
→ 3 秒后他出现在团队里，状态「试用中」，并自动带来第一张任务卡
```

确认弹窗只允许有三块信息，不许再多：

1. **他能交付什么**（一句结果承诺 + 历史达成率）
2. **他要什么权限**（一个可勾选清单：读哪些文件夹 / 能否联网 / 能否写回，默认全部最小）
3. **多少钱**（月成本区间 + 试用期）

**降级但不删除**（移进员工详情抽屉的 tab，想看的人才看）：
- 试岗报告 `TrialReportCard.tsx`
- 授权仪式 `AuthorizationCeremony.tsx` → 压成上面第 2 块的一行
- 五步定制 wizard → 移到「找不到合适的？→ 定制」二级入口
- 团队套餐 / 专家保障 → 「雇人」抽屉里的两个筛选标签

**关键心智：雇佣不是一个项目，是一个动作。** 试岗、评测、认证是**他上班之后**的事，不该挡在门口。

## 6. 改造三：桌面执行要做深（V3 的主要预算都花在这里）

这是用户明确要求"比原来强大得多"的部分。以下每条都直接对应 DeepSeek Harness 或 Codex 的公开机制，请**照着机制做，不要照着界面做**。

### 6.1 Session 是一等对象（来自 Harness：resume / fork / replay）

每次执行 = 一个有 id 的 session，append-only。UI 上必须能：

- **恢复**：断了 / 暂停了 / 关了浏览器，回来接着跑
- **分叉**：「从第 7 步换个思路重来」——保留原分支，新开一条
- **回放**：像看录像一样重放整条轨迹，用于验收和 bad case

工作台上每条执行记录旁边就是这三个按钮。这是 V2 那个「申请→批准→启动→暂停」四步动画完全没有的东西，也是让人相信"它真的在干活"的关键。

### 6.2 Trajectory view 必须是 step 级（来自 Harness）

替换掉 `DesktopWorkstationPage.tsx:283-287` 那 5 行假日志。新的执行流是可展开的 step 列表：

```
▸ 07  browser.open  allowlist://industry-research      1.2s   ¥0.003
▾ 08  file.read     workspace://GTM-2026Q3/accounts.csv 0.4s  ¥0.001
      ├ 思考摘要：需要先确认字段口径，accounts.csv 缺 industry 列
      ├ 参数：{ path: "...", range: "A1:M240" }
      ├ 结果：240 行 / 12 列，3 列有空值      [查看证据 evi_002]
      └ 产物：客户字段差异.csv                [diff 视图]
▸ 09  crm.write     ⛔ 策略拦截，等待审批              —      —
```

每一步可折叠、可跳证据、可从这一步 fork。**证据库不再是一个独立页面，它是这里的一次展开。**

### 6.3 审批模式做成一个下拉（来自 Codex：suggest / auto-edit / full-auto）

这是 Codex 最好的一处产品设计，比 HUMMER 现在的「申请→审批→启动」四步好用一个量级。

会话顶部一个下拉，三档，随时可切，**切换立刻改变后续每一步是否停下来问**：

| 档位 | HUMMER 命名 | 行为 |
|---|---|---|
| suggest | **只建议** (L1) | 每个动作前都问我 |
| auto-edit | **工作区自主** (L2) | 在授权目录内自己动手，出目录 / 联网 / 写回才问 |
| full-auto | **限额自主** (L3) | 预算和白名单内不打断，超限或高危才问 |

默认 L2。**不要**做成一个需要提交、等待、批准的审批流——那是给合规看的，日常用户要的是一个下拉。企业的审批流保留在"高危动作"这一条路径上即可。

### 6.4 沙箱三档 + 工作区绑定要看得见（来自 Codex）

会话顶部常驻一条状态带，任何时候都能一眼看到：

```
📁 ~/GTM-2026Q3  （可写）   🌐 联网：3 个白名单站点   🖥 桌面：只读   💰 ¥2.4 / ¥20   ⏹ 停止
```

对应 read-only / workspace-write / danger-full-access 三档。**目录必须显示真实路径**，不能是 `workspace://` 这种抽象——用户要相信它，就得看见它碰的是哪个文件夹。

### 6.5 Everything is a plugin（来自 Harness）

把 `skills` / `connect` / 模型选择合并成一个 **「能力插槽」面板**，挂在会话和员工上，不再是三个页面：

```
本次会话已装载：
  模型     claude-opus-4-8            [换]
  技能     客户分层 v2.3 (已签名)      [换] [看权限 diff]
  工具     文件读写 / 受控浏览器 / 表格  [+]
  MCP      CRM (只读)  ⚠ 写权限未授予   [申请]
  知识      GTM 知识包 v4               [换]
```

装载 = 一次点击。权限 diff 在装载前弹一次，不做插芯片动画。

### 6.6 岗位说明书就是一个 AGENTS.md（来自 Codex）

员工的「岗位说明书 / SOP」直接是一段**可编辑的 markdown**，员工执行时读它。这比"技能芯片插槽"真实得多，也是唯一一个前端原型阶段就能做成真的东西——用户改一行 SOP，下次执行行为真的变。

员工抽屉里给一个编辑器 + 「上次执行读了这份 v3」的引用。

### 6.7 让人看见「它在我电脑上到底动了什么」

用户要"对桌面的操控更强大"，前端的责任是**让操控变得可见、可信、可中断**：

- **实时画面**：一块屏幕缩略图 / 关键帧，标出它刚点了哪、输入了什么（脱敏）
- **当前前台应用**：`Excel — accounts.xlsx`，一眼知道它在哪个窗口里
- **常驻红色停止条**：执行中在界面顶部常驻，1 次点击立刻收回令牌、冻结在检查点
- **「我来」接管按钮**：一键把控制权拿回来，AI 转为旁观并记录我做了什么

### 6.8 人机换手（handoff）——这是差异化的地方

Codex 和 WorkBuddy 都没做透"人和 AI 在同一个任务上来回换手"。这是 HUMMER 作为**人机协同**系统该拿下的动作，做成一对明确的按钮：

- **AI → 人**：「我卡住了 / 这步需要你判断」→ 生成一张带上下文的交接卡，落到我的待办
- **人 → AI**：「这步我做完了，你从这里继续」→ 我的操作被记进同一条 trajectory，AI 读得到

一条 trajectory 里人和 AI 的步骤**混排、同等公民**。这一条做好了，"人机协同 AI 原生管理系统"就不是一句 slogan。

## 7. 改造四：四个参照系各取一件事，别都抄

| 来源 | V3 只取这一件 | 明确不取 |
|---|---|---|
| **OpenClaw** | 常驻 + 多入口触达：在 IM / 手机发一句话，桌面上的员工就开始干；下班后它还在跑 | 个人助手式的默认高权限 |
| **Hermes** | 记忆候选：任务结束一个「记住这个」按钮，一句话一个作用域，就够了 | 记忆管理中心、五层记忆模型的完整 UI |
| **Codex** | approval mode 下拉 + sandbox 三档 + session fork/resume + diff 审阅 | git / PR / patch 术语暴露给业务用户 |
| **WorkBuddy** | 雇佣即上班；项目内真人与员工共享同一份上下文和能力 | 以个人工作台为中心的产品结构 |
| **DeepSeek Harness** | 插件化能力插槽 + append-only session log + trajectory replay | 直接依赖其 schema 做业务事实源（仍是 developer preview） |

## 8. V3 只做一条演示主线，其余允许是静态的

```
1. 我在飞书发一句：「把这周的线索整理成跟进清单，写回 CRM 前先给我看」
2. 工作台出现一张卡：任务已建，负责人 雪·销售官，模式 L2 工作区自主
3. 我点进去 —— 看见它打开受控浏览器、读我 GTM 文件夹里的表格
   每一步都在 trajectory 里长出来，屏幕缩略图跟着变
4. 走到「写回 CRM」，红字停下：策略拦截，等待审批
   同一屏给我 diff：将新增 12 行、修改 8 行
5. 我批准 → 出成果包（交付物 + 证据 + 成本 ¥2.4 + 回滚方式）
6. 我说「不对，这样分层不行」→ 打回
   → 自动生成 bad case → 我在 SOP 里改一行 → 从第 9 步 fork 重跑 → 这次对了
```

这条线走通了，产品就成立了。**其余页面在 V3 允许是静态占位。** 不要平均用力。

## 9. 给 Codex 的落地纪律

1. **这是一个减法 PR。** 先做第 4 节的降级与合并，跑通 `npm run typecheck` + `npm run build`，再动第 6 节的深度。不要先加后减。
2. **禁止新建第 21 个 PageKey。**
3. **必须复用 `src/features/work-orders/model/` 下已有的 `workOrder.ts` / `resultPackage.ts` 作为唯一事实源。** `DesktopWorkstationPage.tsx` 里的 `WORKSTREAMS` / `WORKSPACE_ITEMS` / `SESSION_COPY` 三个硬编码常量必须被替换掉，否则 V3 又是一个 demo 孤岛。
4. 新增的 session / step / trajectory 需要新的 domain type，按 `AGENTS.md` 的规定：动 `src/lib/types.ts` 或 `api-contract.yaml` 需要 ADR，请**先在 `src/features/` 下新建 `sessions/model/` 自带类型**，不要直接改共享契约。
5. 遵守 `AGENTS.md` 的 UI 约束：沿用现有克制企业视觉 + `lucide-react`，不引入新设计系统。
6. 所有本地资源仍是合成数据，界面必须标记为原型；**不得把前端 mock 描述为已接入真实 Codex Desktop / WorkBuddy / 用户文件 / 浏览器账号 / CRM / MCP。**

- [ ] 雇一个员工 ≤ 3 次点击、≤ 20 秒，之后他立刻出现在团队页并带来第一张任务

- [ ] 任一步骤可 fork 重跑；整条 session 可 replay
- [ ] 审批模式下拉切换后，后续步骤行为立刻改变（L1 每步问 / L2 出界才问 / L3 超限才问）
