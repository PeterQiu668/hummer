# Grill 02 · 群/频道规则 v2：成员应由组织结构推导，而非手工矩阵

日期：2026-07-04 · 状态：v1 矩阵已实现（ROLE_CHANNEL_ACCESS），本文记录 v2 修正方向与 3 个待定问题

## 已实现的 v1（背景）

角色 × 频道访问矩阵（`data/feishu.ts` ROLE_CHANNEL_ACCESS）+ 三处 UI 消费（LeftNav/ChatPage/ChannelList）+ 发言身份跟随角色 + 风险双投 + 空壳群补种子。

## 创始人三问与讨论结论

### Q1 高管分身会议室：「分身-分身-真人高管」同群合理吗？

**结论：分身是主体，真人高管以「列席观察 + 仲裁」身份存在——合理，但发言边界要收紧。**

论证：分身会议室的本质是 **A2A 跨部门协调的可观测投影**，是机器间事件流的人类可读界面。真人高管若参与日常协调，人就变成了 A2A 的瓶颈，分身的意义（先斩后奏、异步预处理）就没了。真人高管在此群的正确权限是：
- 默认**只读列席**（看得见自己分身在如何代表自己）
- 仅两类写动作：`confirm`（确认/打回分身的拆解）与**仲裁**（分身间分歧被 @ 时裁决）
- 日常的「确认分身拆解」更应发生在**真人高管 ↔ 自己分身的 1v1 通道**（或高管工作台，已实现后者），而不是会议室群聊

v2 修正：exec 在 ch-exec 的权限从 rw 细化为 `write: 仅 confirm/仲裁类`（demo 可先用输入框提示表达）；补「分身 1v1 管理通道」概念（channels 增加 dm 类型的 `ch-twin-{execId}`）。

### Q2 一线员工的群，上级领导应该在群里吗？

**结论：应该在——且这暴露了 v1 的根本缺陷：成员不该按「角色类型」手工配置，该按「组织层级」自动推导。**

正确规则：**业务单元作战群成员 = 该单元全体（数字员工 + 一线真人）+ 沿汇报线向上的直属上级及其分身**。可见性沿汇报线向上传递，不向下、不横向。

验证：v1 里吴帆（销售 VP）在 ch-q3（销售作战群）有 rw、但看不到 ch-mkt（市场群）——这不是配置巧合，恰是"按管辖关系推导"应得的结果（市场群的上级是运营 VP 不是他）。v2 应把这个推导显式化：`成员 = zone/部门成员 ∪ managesEmployeeIds 反查的上级链`，而非手写矩阵。

### Q3 老板应该在所有群里吗？

**结论：在——v1 已满足（boss 全部 8 群 rw）。但「在」≠「看」，要补两条细则：**

1. 老板的全群存在是**合规与追责需求**（任何对话可追溯），不是信息消费方式——老板的日常入口是**收件箱**（五类事件聚合），群消息不主动打扰（默认免打扰，@ 和风险除外）。这正是 InboxPage 存在的理由。
2. 心理学细节：老板在场会改变**真人**成员的行为（数字员工无所谓）。是否显示"老板在群"标识 → 待定问题 ③。

## v2 群生成规则（目标态：群不是手工建的）

| 群类型 | 生成来源 | 成员规则 |
|---|---|---|
| 责任链群（总控/分身会议室） | 组织结构 | 总控=老板+老板分身；会议室=全体高管分身 + 真人高管（列席/仲裁） |
| 业务作战群 | 部门/项目单元 | 单元全体 + 沿汇报线上级及其分身 + 老板（免打扰） |
| 风险通道 | 治理策略 | Guardian + 有审批权者（老板/相关高管/审计） |
| 系统通告 | 平台 | 全员只读，Hermes 单向 |
| 临时通道 | 工单/会议 | 专家随工单开关自动进出；会议随会程 |

## 三个待定问题 → 已决策（2026-07-04 二轮 grill）

① **超时确认 → 分级超时 + 默许记账**：低风险超时自动放行，审计记「默许（超时未审）」而非「已确认」，每位高管的**默许率进治理指标**（倒逼认真看或做预授权）；中高风险永不自动确认，超时升级老板收件箱；支持预授权（授权仪式的高管版，机制复用）。原则：默许可以存在，但必须是显式、有记录、可计量的授权形态。
② **专家进出群 → 两阶段 + 上下文切片**（合规硬约束，非偏好题）：接单前只见脱敏工单摘要（不含客户数据）；「开始响应」= 签临时保密与责任协议的动作语义，才入群且仅见工单相关上下文切片（工单创建时点起 + 关联任务消息）；关单即退群、撤销历史访问权，处置记录留工单。
③ **老板存在感 → 静态透明、动态沉默**：群成员面板如实列出老板（谁有权看永远可查，责任链可解释的一部分）；消息流永不显示「正在查看/已读」。理由：完全隐藏与审计可追溯自相矛盾，被发现即信任崩塌；实时提示则寒蝉效应最大化。
