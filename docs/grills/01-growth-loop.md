# Grill 01 · 成长闭环：从「HR 流程模仿」到「进化中心」

日期：2026-07-04 · 状态：方向已定，待实现（下一批 swarm）

## AI 方的四点质疑

1. **拟人化与版本现实错位（根子）**：人需要试岗/转正/淘汰是因为人不可复制不可回滚；agent 可以。"淘汰雪·销售官再招一个新的"，若底层是同一模型+新 SOP，淘汰的只是名字和头像——本质是版本升级穿了 HR 的衣服。
2. **与质量飞轮重复建模**：成长闭环（个体视角）与质量飞轮 bad case→SOP→沙箱→灰度（版本视角）是同一件事的两套互不引用的模型。
3. **7 天日历试岗不合理**：评测需要任务量不是日历时间；7 天唯一说得通的意义是真实环境低风险试运行。
4. **评分可信度被 mock 掩盖**：quality 95 分谁打的、rubric 谁定的——评测资产才是核心 IP，demo 用大数字跳过了最难的问题。

## 创始人立场

- 真正的问题是**闭环流程不清晰**；老板想看到的核心价值是「数字员工能自我进化成长」——进化应该是**独立的数字员工进化模块**，而不是散落在试岗/考核/质量飞轮里。
- 试岗度量：**保留天数 + 双达标**（对外仍讲 7 天，转正条件 = 天数 且 任务量/验收通过率达标）。

## AI 方的反 grill（对「独立模块」的一个警告）

「独立模块」的风险是变成又一个静态展示页——现在的「质量与复盘」（EvolutionFlywheel）就是独立的，它的问题恰恰是**与员工个体没有连接**。老板要看到的不是"进化机制存在"，而是一条**因果链**：

> 员工雪某周一犯错（合同漏标）→ Hermes 归因 → SOP v3→v4 → 沙箱回归通过 → 审批 → 灰度到雪某 → 周四同类任务成功 → 能力分 78→85

没有个体档案和因果链，进化就是不可感知的。

## 结论：进化中心（Evolution Center）三层设计

合并「成长闭环」与「质量飞轮」为一个独立模块，三层视图：

| 层 | 内容 | 老板看到什么 |
|---|---|---|
| 组织层 | 本月 SOP 升级数、平均能力分变化、bad case 修复率、进化 ROI | "我的数字团队整体在变强" |
| **个体层（新增，核心）** | 每个数字员工的**进化档案**：能力分曲线、SOP 版本时间线、bad case→改进→回归→重新认证的因果记录、同岗位对比 | "这个员工上周错、这周对，因为什么" |
| 机制层 | 现有飞轮 5 阶段（detected→optimizing→sandbox→review→shipped） | "进化是受控的，有沙箱有人审" |

### 对外叙事 ↔ 对内机制映射表（拟人化保留为翻译层）

| HR 语言 | 版本化机制 |
|---|---|
| 试岗 | 真实环境灰度运行（≥7 天 **且** 完成任务 ≥N、验收通过率 ≥X% 双达标） |
| 转正 | 认证通过 + 授权仪式 |
| 考核 | 持续在线评测 + 阈值告警（月度报告只是快照） |
| 晋升 | 权限等级提升（只读→审批执行→有限自主）+ 技能扩容 |
| 淘汰 | 连续 N 次进化失败（改进后仍不达标）才触发版本下线；可"返聘"=旧版本重新上架 |
| 成长 | SOP/技能版本迭代（进化中心 = 唯一机制来源） |
